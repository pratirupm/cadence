SSE is for a connected browser. A webhook is for a system that is not connected:
a chat bot, a CI job, a billing service, an internal automation. The server
makes an HTTP request when something happens, and the receiver verifies a
signature before trusting the body.

Webhooks are a durability problem in disguise. The remote server can be down,
slow, or returning 500. The sender must queue, retry, and eventually give up
without blocking the task write that triggered the event.

By the end of this chapter you can:

- register a webhook for a workspace and an event list
- reject non-HTTPS and private-network URLs
- generate a per-webhook secret shown once
- queue a delivery for each subscribed event
- sign a payload with HMAC-SHA256
- retry failed deliveries with backoff and a terminal failure
- explain the SSRF, replay, and duplicate-delivery risks in the current design
- identify where a claim/lease is missing

The Rust lessons are HMAC, URL parsing, a delivery queue, retry arithmetic, and
a worker loop. The security lessons are more important: a user-supplied URL is
untrusted code execution against your network, and a signature without a
timestamp is replayable.

## Why a queue instead of a direct call

The naive implementation is:

```rust
// after the task insert
reqwest::Client::new().post(webhook.url).json(&task).send().await?;
```

It fails in three ways:

1. A slow receiver blocks the task request.
2. A down receiver loses the event with no retry.
3. A receiver that returns 500 has no record of the attempt.

The queue separates “the task changed” from “the receiver was told.” The task
write commits; a delivery row records the obligation; a worker retries it. The
task response does not wait for a third party.

The cost is eventual delivery. The receiver may see the event seconds later, or
never after five failures. Document that; a webhook is not a transactional
guarantee.

## The schema

Create `migrations/0011_webhooks.sql`:

```sql
CREATE TABLE webhooks (
    id TEXT PRIMARY KEY NOT NULL,
    workspace_id TEXT NOT NULL REFERENCES workspaces (id) ON DELETE CASCADE,
    url TEXT NOT NULL,
    secret TEXT NOT NULL,
    events TEXT NOT NULL,
    active INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL
);

CREATE TABLE webhook_deliveries (
    id TEXT PRIMARY KEY NOT NULL,
    webhook_id TEXT NOT NULL REFERENCES webhooks (id) ON DELETE CASCADE,
    event TEXT NOT NULL,
    payload TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'pending',
    attempts INTEGER NOT NULL DEFAULT 0,
    next_at TEXT NOT NULL,
    response_status INTEGER,
    response_body TEXT,
    created_at TEXT NOT NULL
);

CREATE INDEX webhook_deliveries_due_idx
    ON webhook_deliveries (status, next_at);
```

A webhook is per workspace. The `events` column is a comma-separated list such
as `task.created,task.updated`. The secret is generated by the server and stored
in plaintext because the server must sign with it; unlike a password, it is not
a user secret that can be hashed and verified. Treat the database as a secret
store.

A delivery points at a webhook and copies the event and payload. Copying the
payload makes the delivery reproducible even if the task changes later. The
delivery does not have a foreign key to the task; it is an immutable message.

`status` is `pending`, `delivered`, or `failed` in the current code. There is no
`sending` state, which means two workers can select the same pending row. That is
a real gap; the exercises add a claim.

## Registering a webhook

`create` checks the workspace role, validates the URL, and generates a secret:

```rust
pub async fn create(
    &self,
    actor_id: &str,
    workspace_id: &str,
    url: &str,
    events: &[String],
) -> Result<Webhook, WebhookError> {
    let role = WorkspaceService::new(self.pool.clone())
        .role(workspace_id, actor_id)
        .await?
        .ok_or(WebhookError::InvalidUrl)?;
    if !role.can_manage() {
        return Err(WebhookError::Workspace(WorkspaceError::Forbidden));
    }
    validate_url(url)?;

    let webhook = Webhook {
        id: Ulid::new().to_string(),
        workspace_id: workspace_id.to_owned(),
        url: url.to_owned(),
        secret: random_token(),
        events: events.join(","),
        active: true,
        created_at: Utc::now(),
    };
    // INSERT ...
}
```

The not-a-member branch returns `InvalidUrl`, which is the wrong error. It
conflates “you do not belong” with “the URL is bad.” A caller receives a 400
instead of a 403. The exercise asks you to add a `NotMember` or reuse the
workspace error. The behavior is safe; the message is misleading.

Only an owner or admin can manage webhooks. A member cannot register an endpoint
that receives workspace data. A viewer cannot list them either.

The raw secret is returned in the API response once:

```json
{"id":"...","url":"https://example.com/hook","secret":"...","events":["task.created"]}
```

The list endpoint omits the secret. There is no rotate endpoint yet; deleting and
recreating is the rotation path, which means the receiver must update its secret.

## URL validation is security

A webhook URL is a request the server makes to an attacker-controlled host. That
is server-side request forgery (SSRF). The current `validate_url` blocks the
obvious cases:

```rust
fn validate_url(url: &str) -> Result<(), WebhookError> {
    let url = Url::parse(url).map_err(|_| WebhookError::InvalidUrl)?;
    if url.scheme() != "https" {
        return Err(WebhookError::InvalidUrl);
    }
    let host = url.host_str().ok_or(WebhookError::InvalidUrl)?;
    if host == "localhost"
        || host.starts_with("127.")
        || host.starts_with("10.")
        || host.starts_with("192.168.")
        || host.starts_with("169.254.")
        || host == "::1"
        || host.ends_with(".local")
    {
        return Err(WebhookError::InvalidUrl);
    }
    Ok(())
}
```

It does not block:

- `172.16.0.0/12`, a private range.
- IPv6 unique-local (`fc00::/7`) and link-local (`fe80::/10`).
- `100.100.100.200` and other cloud metadata endpoints.
- DNS names that resolve to a private IP (DNS rebinding).
- Redirects from a public URL to a private one.

A production check must resolve the host and validate every returned IP at
delivery time, not only at registration. It must disable redirects or revalidate
each hop. It must also handle IPv6 literals and ports. The book’s check is a
starting point, not a complete SSRF defense; the failure modes say so.

## Dispatching

`dispatch` queues one delivery per active webhook that subscribed to the event:

```rust
for webhook in webhooks {
    if !webhook.events.split(',').any(|subscribed| subscribed == event) {
        continue;
    }

    sqlx::query(
        "INSERT INTO webhook_deliveries
         (id, webhook_id, event, payload, status, attempts, next_at,
          response_status, response_body, created_at)
         VALUES (?, ?, ?, ?, 'pending', 0, ?, NULL, NULL, ?)",
    )
    .bind(Ulid::new().to_string())
    .bind(&webhook.id)
    .bind(event)
    .bind(payload)
    .bind(now)
    .bind(now)
    .execute(&self.pool)
    .await?;
    count += 1;
}
```

The events string is a small filter. A better schema uses a join table or a JSON
array with a containment query; for three event names, a comma list is enough.

`dispatch` is called after web/API task creation, completion, and deletion. It is
not called from sync push, for the same reason SSE is not: the sync path does not
publish. The change log is the only place that sees every task change. A robust
design dispatches from an outbox fed by the change log, not from each handler.
The exercise asks for one version of that.

`dispatch` inserts rows but does not send. It returns the number queued. The
caller can log it; the task response does not wait for delivery.

## Signing

The receiver must know the body came from Cadence. The signature is HMAC-SHA256
over the exact payload bytes:

```rust
pub fn sign(secret: &str, payload: &str) -> String {
    let mut mac = HmacSha256::new_from_slice(secret.as_bytes())
        .expect("hmac accepts any key");
    mac.update(payload.as_bytes());
    hex::encode(mac.finalize().into_bytes())
}
```

The worker sends:

```text
content-type: application/json
x-cadence-signature: sha256=<hex>
```

A receiver recomputes the HMAC with its copy of the secret and compares in
constant time. Do not compare with `==` on strings in a security-sensitive
receiver; use a constant-time comparison. Do not parse and re-serialize the JSON
before checking; the signature covers the bytes, not the semantic value.

The current signature has no timestamp. An attacker who captures a valid request
can replay it later, and the receiver cannot tell. Add a timestamp header and
include it in the signed bytes, then reject old timestamps. The exercise asks for
it; the book’s signature is integrity without freshness.

## Delivery and retries

`deliver_due` selects pending rows whose `next_at <= now`:

```sql
SELECT d.id, d.payload, w.url, w.secret, d.attempts
FROM webhook_deliveries d
JOIN webhooks w ON w.id = d.webhook_id
WHERE d.status = 'pending' AND d.next_at <= ?
ORDER BY d.next_at LIMIT ?
```

For each row, it posts the payload with the signature. A 2xx marks `delivered`.
A non-2xx or a transport error calls `retry`.

```rust
async fn retry(&self, id: &str, attempts: i64, now: DateTime<Utc>, status: u16) {
    if attempts + 1 >= 5 {
        // status = failed
    } else {
        let delay = Duration::minutes((attempts + 1) * (attempts + 1));
        // status = pending, next_at = now + delay
    }
}
```

The first retry waits 1 minute, the second 4, the third 9, the fourth 16. The
fifth failure is terminal. Chapter 10 uses the same shape for reminders; the
constants are a policy, not a protocol.

`deliver_due` has no claim. Two workers can select the same pending row and both
send it. The receiver may see duplicates even without a retry. The fix is a
`sending` state with a lease, exactly like reminders. The current design is
single-worker in `main`, but “we run one worker” is a deployment assumption, not
a correctness guarantee.

`response_body` is never written. The column exists for a delivery log; adding
it is an exercise. A failed response body can contain secrets or attacker HTML;
truncate and sanitize before storing.

## The worker and API

`run_forever` ticks every 30 seconds:

```rust
loop {
    ticker.tick().await;
    if let Err(error) = service.deliver_due(Utc::now(), 50).await {
        tracing::error!(%error, "webhook worker failed");
    }
}
```

`main` runs the reminder and webhook loops together under one shutdown signal.
`worker --once` calls both batches.

The API manages webhooks under `/api/v1/workspaces/{id}/webhooks`:

```text
GET  list   requires admin scope
POST create requires admin scope
```

The create response includes the secret once. The list response does not. Both
also require a workspace admin role; the token scope is not enough.

## Delivery states

| State | Meaning | Next |
| --- | --- | --- |
| `pending` | queued, `next_at` in the future | worker retries when due |
| `delivered` | receiver returned 2xx | terminal |
| `failed` | five failed attempts | terminal |
| `sending` | not implemented | would mean a worker owns a lease |

`attempts` increments on failure, not on claim, because there is no claim. A
delivery can be sent twice before it is marked delivered; the state table makes
that visible. A production queue adds `sending` and `locked_until`, then a
recovery pass.

The `response_status` column stores the last status code; `response_body` is
reserved. A delivery log needs the body, but it also needs a retention policy:
a receiver can return a large HTML error page containing tokens. Truncate,
sanitize, and expire.

## Receiver verification

A receiver should do this before parsing the JSON:

1. Read the raw body bytes.
2. Read `x-cadence-signature`.
3. Recompute `sha256=<hex>` with the shared secret.
4. Compare in constant time.
5. Check a timestamp if the sender includes one.
6. Parse and handle the event.
7. Return 2xx only after the work is durable.

If step 7 returns 2xx before the work is committed, a crash loses the event. If
it returns 500 after the work commits, the sender retries and the receiver must
dedupe. The delivery ID or event ID is the dedupe key. Cadence does not send a
stable delivery ID header yet; the payload’s task ID is not enough for two
identical updates.

## Failure modes you will meet

**`webhook URL must be HTTPS and public`.** The scheme is not https, or the host
is in the blocklist. Use a public HTTPS endpoint. The error is also returned for
a non-member because of the current branch; check membership first.

**The receiver gets duplicate deliveries.** Two workers selected the same
pending row, or a retry happened after a response was lost. Add a claim/lease and
make the receiver idempotent on the event ID.

**The signature does not verify.** The receiver hashed a parsed/re-serialized
body, used the wrong secret, or the sender’s secret was rotated. Sign the raw
bytes and compare the header format exactly.

**A captured request can be replayed.** There is no timestamp or nonce. Add a
signed timestamp and reject stale requests.

**A public hostname resolves to 127.0.0.1.** The validator checked the hostname
string, not the resolved IP. Resolve at delivery time and validate every address.

**A redirect reaches a private address.** `reqwest` follows redirects by default.
Disable or revalidate each hop.

**A delivery is stuck pending forever.** The worker is not running, or `next_at`
is far in the future. Check `worker --once` and the row.

**The secret appears in a list response.** The list handler must omit it; only
create returns it. Do not serialize the `Webhook` struct blindly.

**The delivery log grows without bound.** There is no retention. Delete delivered
rows after a window, or archive them. Do not delete pending rows.

## Under the hood

HMAC is a keyed hash: only someone with the secret can produce a valid tag.
SHA-256 provides collision resistance; HMAC prevents length-extension attacks
that a naive `sha256(secret || payload)` would allow. Use a library; do not
compose your own.

A webhook receiver has two jobs: authenticate the request and make the handler
idempotent. The signature proves the sender; an event ID or delivery ID lets the
receiver ignore a duplicate. Cadence does not send a stable delivery ID header
yet; the payload’s task ID and event are not enough for two identical updates.

The delivery queue is a small outbox. A more robust design writes the outbox row
in the same transaction as the task change, then a worker drains it. The current
handlers call `dispatch` after the service returns, so a crash between the task
commit and the dispatch loses the webhook. The change log already solves this
for sync; use it for webhooks too.

## Exercises

1. **Add a claim/lease.** Add `sending`, `locked_by`, `locked_until`; claim with
   a lease; recover expired leases. Test two workers.
2. **Add timestamps to signatures.** Send `x-cadence-timestamp`, include it in
   the HMAC input, and reject requests older than five minutes.
3. **Resolve and validate IPs.** Resolve the host at delivery time and reject
   private, loopback, link-local, and metadata addresses. Disable redirects.
4. **Add a mock delivery test.** Use a local HTTP server with a test-only
   validator override. Assert the signature, body, retry on 500, and success on
   200.
5. **Dispatch from the change log.** Write a worker that reads changes and creates
   deliveries once, independent of web/API handlers. Test a CLI sync update.
